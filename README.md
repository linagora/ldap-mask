# ldap-mask

An LDAP proxy that **substitutes a fictitious local identity for a real
upstream identity**: the client binds with a local DN and password, the proxy
verifies the password locally and then rebinds to the destination directory
with the real DN and the real password.

The design — principle, scope, BER format, security — is detailed in
[`DESIGN.md`](DESIGN.md).

## What it does / what it does not do

| Does | Does not do |
|---|---|
| Substituted simple bind (local DN → real DN) | Client-side StartTLS (refused with `unwillingToPerform`) |
| Listener **cleartext LDAP or LDAPS**, your choice | SASL (relayed as-is, not substituted) |
| Upstream **`ldap://` or `ldaps://`** | Operation or subtree restriction |
| Verbatim relay of everything else (searches, controls, paged results, extended operations) | Root DSE / WhoAmI / referrals rewriting |
| Several local → remote mappings | |
| Local password stored hashed (bcrypt) | |
| Remote password injected via environment variable | |

This is a debug tool: **all four combinations** of listener and upstream are
usable. TLS is available on both sides, never forced.

| Listener (`listen`) | Upstream (`upstream.url`) | |
|---|---|---|
| `ldap://` | `ldap://` | all cleartext |
| `ldap://` | `ldaps://` | TLS on the upstream leg |
| `ldaps://` | `ldap://` | TLS on the client leg |
| `ldaps://` | `ldaps://` | all TLS |

Each cleartext leg is reported with a `WARN` at startup.

The known leaks not addressed in v1 (Root DSE, `WhoAmI`, referrals) are
documented in [`DESIGN.md` §6](DESIGN.md#6-security--what-the-proxy-does-not-protect).

## Quick start

### 1. Build

```bash
go build -o ldap-mask .
```

### 2. Generate the bcrypt hash of the local password

The password is read from standard input, or passed as an argument
(`-hash <password>` and `-hash=<password>` are equivalent):

```bash
# Recommended: input on standard input
./ldap-mask -hash

# Or as an argument
./ldap-mask -hash 'hunter2'
```

The output is the bcrypt string to copy into `local_password_bcrypt`.

> **A password passed as an argument is visible** in the process list (`ps`)
> and in the shell history. The proxy warns about this on standard error; keep
> that form for experiments. An unexpected positional argument — for example
> `./ldap-mask hunter2`, without `-hash` — is refused with an explicit error,
> never silently ignored.
>
> Reading from standard input is not silent either: **v1 does not disable
> terminal echo**, so the password is displayed as you type. To avoid that, feed
> `-hash` through a pipe: `printf '%s' "$PASSWORD" | ./ldap-mask -hash`. An empty
> password is refused — its hash would accept any bind without a password.

### 3. Write the configuration

```yaml
# Listen address. The scheme is MANDATORY and decides the mode:
#   ldaps:// → TLS terminated on the proxy (the tls: block is then required)
#   ldap://  → cleartext (the tls: block is ignored)
# It has no default: without it, a cleartext listener cannot be told apart from
# a TLS one, and getting it wrong would mean serving cleartext through a proxy
# you believe to be encrypted. The default port follows the scheme (636 / 389).
listen: "ldaps://0.0.0.0:1636"

# TLS certificate presented to the client (required if and only if ldaps://).
tls:
  cert_file: /certs/proxy.crt
  key_file:  /certs/proxy.key

# Destination directory (ldap:// or ldaps://).
upstream:
  url: "ldaps://ldap.internal:636"
  ca_file: /certs/internal-ca.crt     # CA that signed the upstream certificate
  insecure_skip_verify: false         # false, deliberately

# Table of local → remote substitutions.
mappings:
  - local_dn: "cn=test-admin,dc=test"
    local_password_bcrypt: "$2a$10$..."          # generated by `ldap-mask -hash`
    remote_dn: "cn=admin,dc=example,dc=com"
    remote_password: "${LDAP_ADMIN_PASSWORD}"    # resolved from the environment

# A DN absent from the mapping is refused (49), not forwarded.
allow_unmapped_bind: false
```

`${VAR}` is resolved from the environment at load time: the remote password
is never written in cleartext on disk. A variable that is referenced but
absent makes **startup fail** rather than starting with an empty value.

### 4. Run

```bash
LDAP_ADMIN_PASSWORD='the-real-admin-password' ./ldap-mask -config config.yaml
```

For a fully cleartext test bench — the typical debug case — simply change both
schemes, without touching anything else:

```yaml
listen: "ldap://0.0.0.0:1389"
upstream:
  url: "ldap://ldap.internal:389"
```

At startup, the proxy then reports every leg left in cleartext on standard
error.

## Options

| Option | Default | Description |
|---|---|---|
| `-config` | `config.yaml` | Path to the configuration file. |
| `-hash` | — | Generates a bcrypt hash; password read from standard input or passed as an argument. |
| `-version` | — | Prints the version and exits. |

By default the proxy **refuses** `insecure_skip_verify: true` upstream. To
allow it anyway, it must be requested explicitly:

```bash
LDAP_MASK_ALLOW_INSECURE=1 ./ldap-mask -config config.yaml
```

This is the only way to enable that option — reserved for troubleshooting.

## Docker

```bash
docker build -t ldap-mask .

docker run --rm \
  -p 1636:1636 \
  -v "$PWD/config.yaml:/etc/ldap-mask/config.yaml:ro" \
  -v "$PWD/certs:/certs:ro" \
  -e LDAP_ADMIN_PASSWORD='the-real-admin-password' \
  ldap-mask
```

In the image, the container listens on port **1636**, expects its configuration
at **`/etc/ldap-mask/config.yaml`** and runs as user **`nonroot`**. The remote
password is injected at launch via `-e` → `LDAP_ADMIN_PASSWORD` (adapt the name
if your configuration references another `${…}` variable).

> **TLS key permissions.** Distroless `nonroot` is uid **65532**: a private
> key in `0600` owned by your user is not readable by the container, which then
> refuses to start with `loading TLS certificate: … permission denied`. Two
> solutions: run the container as your own uid —
> `docker run --user "$(id -u):$(id -g)" …` — or grant the container's group
> read access to it. Do not set it to `0644`: it is a private key.

The proxy **refuses to start** if a variable referenced by `${…}` is absent,
rather than starting with an empty value — the message names the offending
mapping.

## Verification

With the **local** pair (`cn=test-admin,dc=test` / `hunter2`):

```bash
ldapwhoami -H ldaps://localhost:1636 -D 'cn=test-admin,dc=test' -w 'hunter2'

ldapsearch -H ldaps://localhost:1636 \
  -D 'cn=test-admin,dc=test' -w 'hunter2' \
  -b 'dc=example,dc=com'
```

The bind must succeed and `ldapsearch` must return the usual entries. On a
cleartext listener, simply replace `ldaps://localhost:1636` with
`ldap://localhost:1389` — the rest is identical.

> **Warning** — `ldapwhoami` displays the **real DN** of the identity bound
> upstream (`cn=admin,dc=example,dc=com`), not the local DN. This is not a bug:
> it is the `WhoAmI` leak documented in
> [`DESIGN.md` §6.3](DESIGN.md#6-security--what-the-proxy-does-not-protect). The
> password itself never leaks.

## Tests

```bash
go test ./...                # unit tests
go test -race ./...          # with the race detector
go test -tags=e2e ./...      # compiles the integration, but skips it without LDAP_MASK_E2E=1
```

The integration tests (`-tags=e2e`) run against a **real** OpenLDAP directory
and **real** clients (`ldapwhoami`, `ldapsearch`); they only start if
`LDAP_MASK_E2E=1`. See `.github/workflows/e2e.yml` for the expected variables.

## Security

- **Keep the proxy out of the agent's reach.** Shell access on the same
  machine allows reading the configuration and the real password.
- **Encrypt both legs.** Client → proxy over `ldaps://`, proxy → upstream over
  `ldaps://`. Whenever the upstream leg is cleartext, the real admin password
  crosses the network unencrypted — that is the leg that matters most. Both
  modes exist because this is a debug tool, but every cleartext leg is reported
  at startup.
- **Secret in an environment variable**, never written on disk.
- **No failure counter and no lockout in v1.** bcrypt bounds the rate, but the
  proxy must not be exposed beyond a trusted network.

The details of these points and of what the proxy does not protect are in
[`DESIGN.md` §6](DESIGN.md#6-security--what-the-proxy-does-not-protect).
